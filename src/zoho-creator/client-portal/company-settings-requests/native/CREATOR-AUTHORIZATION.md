# Creator authorization seam: source proposal

Status, 2026-10-12: offline implementation and proposed native source/schema only. No native import, Custom API, widget, form, permission, user, grant or lifecycle configuration was created. `Portal_Test_ResolveCompany` remains fixture-only; it is absent from this repository checkout and was not changed or used as authentication.

## Concrete composition

[`../creator-authorization-projection.js`](../creator-authorization-projection.js) supplies the projection missing before the existing `services.readAuthorization()` callback. It reuses `resolveProtectedCompanyLinks` for operation grants and canonical joins. It changes neither the timed producer nor v1 binding serialization. The callback must freshly derive native caller context and read a complete protected registry on every invocation, then call `projectCreatorAuthorization(Account, sessionReceipt, registryReceipt, policy)`. The existing timed producer checks invocation intervals, repeated identity/revisions and deadlines. A browser must never provide these receipts or policy; structural checks and `callerContextQualified: true` are trusted server assertions, not authentication.

The session receipt is exactly `{ environment, organizationId, observedAt, complete, callerContextQualified, nativeSubjectId, incarnationId, emailAddresses, username, permission }`. The registry receipt is exactly `{ environment, organizationId, observedAt, complete, bindings, grants, accountLinks, contactLinks }`. Its grant/link rows retain the existing offline contract. Binding rows are exactly `{ principalId, auditActorId, nativeSubjectId, incarnationId, emailLookup, username, active, revision }`. Policy is exactly `{ expectedEnvironment, expectedOrganizationId, asOf, maxAgeMs, allowedPermissions }`; use the protected current server clock and exact operation-permission allowlist. All IDs remain strings.

The projector requires one native email in a LIST and one exact binding including inactive candidates, unique native subject/internal principal/human actor, exact native subject **and incarnation**, reviewed username corroboration, active binding and allowed current native permission. Email is only the lookup: internal principal and actor come from the protected binding, never a hash/email/username. Unknown caller context, partial reads, stale/future/wrong-tenant facts, duplicates and missing lifecycle evidence deny. A fresh registry read cannot refresh a cached session: the output uses the oldest constituent observation time. Neither this projection nor the diagnostic probe supplies CRM receipt provenance or durable acceptance.

## Native source and one schema choice

[`portal-caller-context-probe.deluge`](portal-caller-context-probe.deluge) is a concrete zero-argument, read-only native function body for a separately authorized qualification probe. It calls all three documented native tasks and always returns `callerContextQualified: false`; exception details are suppressed. Returned native labels stay private, are compared with the same caller's known session by the operator, and are not logged or copied into GitHub. This is a diagnostic, not a production authorization function.

Official capability checked 2026-10-12: [`loginUserEmailid()`](https://www.zoho.com/deluge/help/misc-statements/get-portal-user-emailid.html) returns LIST; [`loginUserName()`](https://www.zoho.com/deluge/help/misc-statements/get-portal-user-username.html) and [`loginUserProfile()`](https://www.zoho.com/deluge/help/misc-statements/get-portal-user-permission.html) return username and permission text. These documented tasks do not establish immutable user/lifecycle identity. [Creator Custom APIs](https://help.zoho.com/portal/en/kb/creator/developer-guide/microservices/custom-api/articles/understand-custom-apis) support a Portal users scope callable only from a widget; the [widget API](https://www.zoho.com/creator/help/js-api/v2/custom-api.html) exposes `ZOHO.CREATOR.DATA.invokeCustomApi`. Custom APIs execute Deluge, not this Node module. Those docs do not prove which caller the Deluge tasks observe in this candidate invocation or qualify a Node transport. Do not expose internal identity evidence to a widget and then round-trip it as trusted server data. A protected server-to-server bridge or separately parity-qualified native implementation remains necessary.

The **one ownership decision before native implementation** is where to keep protected principal bindings, current operation grants and reviewed canonical links. Recommended proposal: four separate operator-only Creator forms in [`creator-authorization-schema.proposed.json`](creator-authorization-schema.proposed.json), leaving business Account/Contact records and fixture forms unchanged. This keeps native authorization reads local, but needs new schema, proven uniqueness/concurrency controls and lifecycle integration. A separately authoritative server registry avoids adding Creator forms but introduces a qualified transport, revocation availability and another operational owner. Neither choice is installed or approved by this proposal.

The proposed schema requires immutable internal principal/actor, a qualified native subject and account incarnation, exact reviewed email lookup, current active state and revisions. Do not infer lifecycle IDs from the three labels, `Portal_User_ID`, email, a timestamp, Billing `Customer_ID` or fixture user keys. A recreated account cannot reuse an old principal. Email changes require revocation and reviewed rebinding. Retain inactive tombstones and deny duplicate candidates. Changing any binding identity/lifecycle state must revoke its current grants and advance grant revisions before reactivation; serialize provisioning or keep the binding inactive. Binding `revision` is retained in the registry but does not add an attribution field: existing grant revisions carry lifecycle transitions into the unchanged timed producer. Native concurrency and controlled revision issuance are unqualified.

No blanket access request is needed.
