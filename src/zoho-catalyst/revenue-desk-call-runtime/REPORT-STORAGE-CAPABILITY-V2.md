## Bounded multipart configuration transport

Reviewed part sizes are 100, 200 or 400 ASCII characters; preparation defaults to 200. This is an application choice, not a documented provider maximum. Maximum reconstructed bytes remain 4096; maximum parts are 41. Every nonfinal part must have the declared size; the final part must have the exact remainder. Missing, extra, malformed and conflicting legacy/part formats are held before parsing. Full raw SHA256 verification rejects mixed or altered content before schema, identity or provider dispatch. This legacy representation introduces no decompression or dependency; the optional compact representation below uses bounded native Node zlib.

Independently verify full absence. A partial cleanup holds qualification. The old raw JSON format remains accepted only with no part-prefixed keys.

Transport success or shorter values establish neither provider size limits nor runtime acceptance. Preserve prior consumed or aborted claims. One new operation requires its own reviewed nonce and fresh protected evidence; no existing admission, retry or authority semantics change.


## Optional all-field tuple transport and complete-size preflight

`encodeStorageBinding(raw, {partSize:400, format:'tuple-v1'})` encodes the existing schema-3 binding's **all 41 scalar values**, in a fixed versioned field order. No value is omitted, defaulted, derived from another field or taken from an environment pin. The object structure/field names are defined by version one; every original value is carried, including repeated digests/times, identity, authority, provenance and expiry. The encoder rejects extra/missing/reordered object keys, duplicate JSON keys and any raw serialization that cannot be reconstructed byte-for-byte. Original JSON and `parts-v1` remain supported independently.

The tuple is canonical minified JSON, compressed with native `node:zlib` raw deflate and encoded as canonical Base64. The JSON activation key contains `tuple-v1:<part-size>:<count>:<encoded-length>:<tuple-byte-length>:<original-raw-byte-length>`. The same numbered part keys, 100/200/400 sizes, maximum 41 parts and 4096-byte original/raw, tuple and encoded bounds remain. Decompression has a fixed 4096-byte output limit; actual consumed compressed bytes must equal the input, rejecting trailing garbage or a second stream. UTF8, canonical tuple JSON, exact count/types, schema version, declared lengths and the reconstructed ASCII/raw bound are checked before the existing binding parser. The full original-byte SHA256, capability/schema/identity/expiry validation, admission claims and thirteen-request ceiling are unchanged. Compressed-byte determinism is not authority and is not required.

Native zlib needs no package installation or grant. The existing Node24 targets support `info` and `maxOutputLength`; trailing data is rejected using consumed-byte accounting rather than a newer-runtime-only option. See [Node zlib options and byte accounting](https://nodejs.org/api/zlib.html). Extracted-runtime verification must exercise the actual packaged codec and qualification factory separately from source tests.

Short part values alone do not establish that the total configuration fits. `preflightStorageEnvironment` is a pure offline gate with a **3578-byte engineering planning budget**, chosen for margin below an observed successful configuration. This is not a documented Zoho limit or a capacity guarantee. It takes complete independently observed serialized-map byte/count metrics and serialized key/value contribution lengths for only the controlled diagnostic and descriptor keys. Never transmit/store a credentials map or unrelated key/value pairs. The safe metadata projection must include any existing storage marker/hash/part-prefix keys too: such a staged/armed baseline is rejected, not overwritten. Account for UTF8, escaped JSON, braces/commas, both descriptor pins, every part, raw hash and final marker. Existing descriptor replacements are counted; planned sender-pair removal is explicit and requires both contributions. The gate verifies transport/raw-hash consistency and rejects an over-budget final map. Its result neither authorizes removal nor asserts freshness, identity, permission or provider capacity.

Before local one-use preparation, perform exact candidate sizing with a fresh safe baseline. Repeat the final planned-size calculation after any configuration change, including diagnostic retirement, and immediately before staging. No binary-search writes, partial acceptance or automatic Save retry are added. Marker-last, disarm-first, independent part/hash/marker readback and ambiguous-write/no-replay rules above remain unchanged. Preserve all prior immutable drafts, evidence, aborted preparation claims and installed archives; this source adds no live authority.
