# Two-stage Development storage preparation

This offline tool separates static review and transfer from final preparation. It changes no deployed runtime, token lifetime, product limit or live authority.

The private kit supplies reviewed pins/templates. `review(input,{root,at})` validates safe original metadata, mapping, controls, installed artifact and complete-map accounting. Historical observations retain their original times; the result has no nonce, expiry, binding or claim. `writeReview` creates only an immutable non-executable review file.

Static review also accepts explicit absence of both descriptor pins: both presence flags and both match flags must be false. This records the reviewed logical descriptor as proposed configuration, not a provider-assigned or observed live deployment ID. Missing flags on this absence path, partial presence and mismatched descriptors hold; supplied presence flags must also agree with asserted matches. Legacy matching records without presence flags remain supported. Active preparation still requires both matching pins. After descriptors are configured and independently read back, create a new static review from the actual changed controls and complete-map sizing, then re-attest all six roles. A freshness witness cannot conceal that state change.

When desktop inputs, native Library output and the cloud executor are ready, perform actual independent current reads. `prepare(input,{root,at,codec})` compares recursive canonical state hashes with the original review, retains both records and requires new observations with safe provenance references and record digests. Provenance references are audit records, not provider signatures or proof manufactured by this tool. A trusted operator must retain the actual read receipts. Changing timestamps alone is never a qualifying read.

The final phase selects its finite window only from the exact reviewed Development storage-diagnostic binding: schema 3 retains 15 minutes; schema 4 explicitly selects 60 minutes for this fixed synthetic diagnostic. Unknown schemas and other environments hold. Exact source/tenant/control checks, sizing preflight, one immutable local claim and runtime durable admission remain. Its ceiling remains 13 DataStore attempts, three retained synthetic rows and one admitted invocation. State changes hold for a new review; a consumed or ambiguous final claim is never renewed. Static review cannot use the final writer.

Static Library-backed files still use supported materialization or the user's explicit local path. Messages must not reconstruct those bytes. Newly generated sanitized observations can use the supported delegation channel only after an actual synthetic UTF8 byte/hash probe passes. `verifyObservationText` checks exact text bytes, including Unicode, whitespace and line endings; a local JSON round-trip does not qualify a remote channel.

Final output retains `reattestation-private.json` containing the original snapshots, current records and provenance, alongside the exact binding/caller/manifest. Keep these private. Source tests use synthetic snapshots only. No provider is invoked and no configuration is armed by this tool; live execution and disarm remain separately coordinated.

Before an expiring claim is created, verify the output recipient is ready. Native Library host upload success is separate from unsupported Windows xattrs. Keep returned Library identity/version with the local hash; never retry a successful create because metadata application failed. Stop if publication is unknown or the remaining machine window cannot support staging and verification.

## Compact current-read witnesses and automated finalization

Before requesting fresh reads, discover the supported `mcp__codex_apps__library_create_library_file` host-upload tool and run `storage-qualification-local-runner.js preflight <existing-python>` on the actual executor. This uses only Python's standard ZIP library and checks a synthetic archive round trip; it installs nothing. Retain a local discovery record with `toolName` and `supportedHostUpload: true`. Discovery is not an upload or provider-permission proof.

The compact witness envelope is `{schemaVersion:1, kind:"current_read_witnesses_v1", staticReviewSha256, witnesses, sha256}`. `witnesses` has exactly the six original roles. Each witness has exactly `role`, `method:"independent_current_read"`, `reference`, numeric millisecond `observedAt`, `stateSha256` and `recordSha256`. The envelope hash is the recursive canonical SHA256 of the other four fields. Each state hash covers the genuine current record with only its permitted top timestamp removed; each record hash covers that complete current record. The original static review file hash must match. Retain actual independent-read receipts outside the public repository. Hashes establish consistency, not authenticity or independent-read provenance by themselves.

`prepareWitnesses` derives each record explicitly from the retained original plus the witnessed observation timestamp. It verifies original state, current state and complete-record hashes, reference format, role, strictly newer timestamps and all existing readiness checks. It retains originals and the complete witness envelope with `evidenceForm: derived_original_plus_current_read_witness_v1`; it does not describe derived bytes as a freshly transferred provider record. Any changed state requires a complete current record and new static review. This path never reconstructs Library artifacts or invents observation timestamps.

All six evidence freshness horizons and the proposed expiry must each leave at least ten minutes before any generated nonce and again immediately before the immutable claim. Expiry must be within every actual observation plus the schema-selected diagnostic window and within preparation time plus that same bound. No observation is restamped. The threshold is conservative, not a measured provider/UI staging guarantee. Short windows hold without a claim, and a failed or expired existing claim is never renewed.

Schema 4 changes this diagnostic's authority duration; it is not merely an encoding version. Tuple-v1 keeps its exact 41-field shape and raw-content hash. The runtime's shared capability validator retains the 15-minute default unless supplied the exact fixed diagnostic contract with matching Development app/config/environment. Request deadlines (at most 60 seconds), source and tenant pins, internal actor, unique synthetic namespaces, attempt/row ceilings and single admission are unchanged. Credentials, bootstrap/recipient/report-delivery windows, customer workflows and the seven-day/25-call product rules are unaffected.

Before using schema 4, independently review and install the exact new disabled Development Controller candidate with its bundled Analytics code and unchanged authentication composition; no activation follows installation automatically. A schema-4 binding fails against older runtime code, and a changed source requires new genuine installed-state evidence and static review. Disarm marker first, independently verify absence, preserve consumed claims/receipts, and restore the prior archive and protected prestate when rolling back. Schema 3 is the compatible default; rollback never revives an expired binding or reuses an old nonce.

The final local input is `{staticReviewFile,witnessFile,expiresAt,operatorReady:true,stagingDirectory,destination,archive}`, with absolute private output paths that do not already exist. Run `storage-qualification-local-runner.js prepare <existing-python> <input-json> <kit-root> <discovery-json>`. The runner rechecks the actual packaging path before processing witnesses, then performs witness validation, preparation, claim creation and ZIP generation without manual record rewriting. The output ZIP is verified against every prepared file and its SHA256 is returned. Publish that one ZIP through the discovered native Library tool immediately; Library publication remains an orchestration operation, not a hidden network action inside this offline runner. If packaging fails after a claim, retain the claim/files and report; do not run finalization again. No provider staging, activation or invocation is part of this runner.
