# Immutable ReportRuns successors

This source revision uses the existing ReportRuns table and its unique IdempotencyKey column. Live table uniqueness, encrypted/private payload access and the effective runtime principal still require independent qualification. No schema, grants or installed bindings are changed by this source.

Root slots retain revenue-desk-report-v1:<logical key>, contending with old writers. A new encrypted payload envelope has a fresh owner. Later slots use revenue-desk-report-v2:<logical key>:<ten-digit sequence>. Slot identity never includes candidate state. Each transition dispatches one insert and independently reads that exact slot; only its own envelope authorizes continuation. A losing insertion returns null. Read accepted history with get; never reinterpret a losing insertion as ownership.

No UPDATE, mutable head pointer, takeover lease or automatic mutation retry exists. Unknown insertion or missing/mismatching readback holds reconciliation. Provider-dispatch phases remain consumed across retries; completed imports, CRM effects, PDF conversions, uploads and mail are not replayed. Legacy plaintext-state roots remain exact and read-only. Their old approved drafts/receipts are retained; an attempted insertion cannot replace them.

Head selection reads the root and latest two successor rows, validates the current edge, predecessor row digest and root commitment. This is bounded current-edge validation under trusted append-only writers, not a complete administrative-tampering audit of every historical ancestor. A separate audit/reconciliation is required for altered history.

The successor head query uses Catalyst ZCQL's literal `*` suffix wildcard. The store, query allowlists and provider fixtures share the exact operation namespace, numeric descending version order and two-row limit. SQL `%` is rejected before dispatch; interpreting it as a prefix match in an offline fixture would hide a missing-successor result.

Thus an attempt is bounded to at most 26 added rows and 40 reads, including failures; there is no invented lifetime cap across separately authorized corrections or manual resends. Existing six-failure backoff still bounds automatic failed attempts. Compared with six mutable logical roots in the cold fixture, immutable storage adds eight rows for that first revision. Payload envelopes remain within the existing 9,500-byte bound and public status values are unchanged.

Focused tests cover distinct/identical contenders, root ownership, unknown accepted insertion, lost insertion, current-edge corruption, legacy preservation, isolation, physical budgets, concurrent PDF pairs, ambiguous rendering, stored-byte mismatch and corrected immutable revisions. ## Runtime qualification boundary

Schemas 3, 4, 6 and 7 use a single physical transport per qualification. It admits at most two active requests, tracks pending managed authentication and native request closure, and joins cancellation/drain before completing or reporting a hold. A logical timeout does not free a physical slot. Schema 5 retains its sequential diagnostic path and strict acknowledgement/readback behavior. Neither path retries an ambiguous mutation.

The current storage testing workflow uses [binding schema 7 and activation schema 2](REPORT-DORMANT-STORAGE-ACTIVATION.md#untimed-qualification-protocol-schema-7). Staging alone cannot construct transport. There is no pre-execution activation window, evidence-age cutoff, setup deadline or minimum dispatch headroom. Observation timestamps remain audit metadata, not time-based execution authority. Before irreversible consumption, reconcile the exact source, target, access, scope, actual aggregate spending and original unconsumed ledger; then consume that exact operation and activation once and Execute once. Elapsed setup time alone never requires renewed approval, replacement settings or a new attempt. Changed facts, revoked access, mismatched source, exhausted cost capacity or consumed identity still block execution.

Runtime timeouts begin with invocation: 25 seconds for the operation, three seconds per request/authentication and one second for owned drain. Physical limits remain 13 starts, five insert attempts, eight reads, two active requests and at most five new synthetic rows. Cancellation or timeout does not rule out a late server-side write and never authorizes retry.

Schema 6 remains historical compatibility only. Its consumed identity must never be converted, reset, rearmed or replayed. A new schema-7 operation requires its own admitted identity while preserving all original ledger history, liabilities and the unchanged aggregate spending cap. Renewed observations cannot change a staged operation's permanent admission key.

The Controller initializes one HTTPS bootstrap before importing application code. The release builder includes that bootstrap and the physical transport in the Controller's own reporting dependency tree. Target identity comes from an issued, app-bound capability and validated managed runtime scope, never public tenant literals or caller-provided transport options.

Managed runtime admission accepts only canonical stable `v24.MINOR.PATCH` strings with nonnegative safe-integer components and no leading zeros, suffixes or whitespace. Other majors, prereleases, build labels, missing values and malformed versions remain held as `node_version` before physical construction. The local verifier and CI retain the exact Node `24.19.0` binary/toolchain pin for reproducible builds and tests. This deliberately replaces the former managed patch-equality policy; it does not broaden the pinned SDK or change authentication, target, replay, request, concurrency, deadline or drain controls.

As reviewed on 2026-10-13, Catalyst's [Functions Stack](https://docs.catalyst.zoho.com/en/serverless/help/functions/stack/) and [Runtime Support Policy](https://docs.catalyst.zoho.com/en/serverless/help/functions/runtime-support/) document Node.js 24 without promising a worker patch. [Function Overview](https://docs.catalyst.zoho.com/en/serverless/help/functions/implementation/) and the package stack identify the selected stack, not the executing process version. A BasicIO observation cannot establish the AdvancedIO version. No minimum minor version is inferred from that observation.

This is a compatibility policy, not a runtime-binary, TLS or behavioral attestation. The [Node release policy](https://github.com/nodejs/Release#release-plan) normally keeps changes compatible within a major line but permits rare breaking security or bug fixes. Independent bootstrap/SDK continuity checks and conservative physical settlement remain required. Version-label fixtures exercise admission on the pinned local binary; they do not claim execution on every admitted binary or vendor acceptance. AdvancedIO qualification and selective configuration cleanup remain separate release prerequisites.

A separately retained synthetic BasicIO run observed two overlapping rounds in one invocation: five insert attempts and eight reads, with one admission row and two report rows confirmed afterward. Its original inactive package was restored. This is bounded storage evidence for that harness, not acceptance of the canonical AdvancedIO entrypoint, managed HTTP context, runtime build, ingress or installed configuration. The source integration does not create a qualified private binding or enable delivery. AdvancedIO acceptance, CRM compare-and-swap, PDF/WorkDrive and delivery remain separate release gates.

Protected reporting/delivery bindings require claimQualification.mechanism=unique_insert_successor_v1 plus qualified status, a private evidence digest and finite expiry. Configuration alone cannot manufacture that qualification. All delivery, auto-delivery and CRM projection switches remain disabled until their separate gates pass.

The smallest proposed synthetic Development storage proof is four insert attempts and at most eight reads, touching only one fresh synthetic logical operation with root and successor slots. Two contenders attempt the same root, then the same successor; exact readbacks must show one owner per slot and two immutable rows total. No customer data, provider conversion/upload/mail or Retell action belongs to that proof. Ordinary approved Zoho testing has no blanket unknown-quota hold; a known new paid service, upgrade or purchase needs its distinct approval. Stop on principal mismatch, uniqueness failure, ambiguous dispatch, projection mismatch or unexpected effects; retain rows/evidence and keep execution disabled rather than blindly retrying or deleting history.
